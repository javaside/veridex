# 企业级 RAG 平台设计规格

- 日期：2026-08-09
- 状态：规格已确认
- 产品代号：Veridex
- 技术基线：Spring Boot 4、Spring AI 2.0 GA

## 1. 文档目的

本文定义从零建设企业级 RAG 平台第一阶段的产品范围、架构、领域模型、核心链路、技术选型、质量体系、安全边界和交付标准。

功能全景用于明确长期边界，但不代表第一版全部开发。第一版应通过一个真实场景验证数据、检索、回答和质量闭环，再逐步平台化。

## 2. 已确认的背景与约束

### 2.1 产品定位

建设通用企业 RAG 平台，首个样板场景为企业制度问答。

系统面向中型企业单企业私有部署，设计基线为：

- 500–5000 名用户；
- 10 万–100 万份文档；
- 首期团队 4–6 人；
- 首期周期约 3 个月；
- 同时兼容企业内网模型和受控外部模型 API；
- Java 承担平台和 RAG 主链路；
- Python 仅作为复杂 OCR、版面分析和多模态解析的可选扩展服务。

### 2.2 产品目标

第一版必须证明：

1. 真实企业资料能够稳定进入系统；
2. 系统能够检索到正确证据；
3. 回答严格基于授权资料并提供可定位引用；
4. 依据不足时能够明确拒答；
5. 错误答案可以回放、归因、评测和修复；
6. 文档、索引、配置和评测结果可复现、发布和回滚；
7. 系统可以在企业环境中部署、监控、备份和恢复。

### 2.3 非目标

第一版不建设：

- 多租户 SaaS、计费和套餐；
- 通用 Agent 平台、可视化工作流和插件市场；
- GraphRAG、知识图谱和模型训练平台；
- 全量多模态、视频和音频知识库；
- 数十种企业连接器；
- 段落级 ACL；
- 多地域容灾和跨集群控制面；
- 自研模型推理引擎、向量数据库、消息队列或对象存储。

## 3. 建设路线决策

采用“场景优先、逐步平台化”路线。

第一阶段围绕企业制度问答完成端到端闭环，同时将知识、检索、生成、评测、权限和模型能力设计为清晰模块。基础设施采用成熟组件，平台核心领域模型和治理能力自行建设。

不采用底座优先路线，原因是缺少真实用户和数据时容易形成技术组件集合，并产生错误抽象。不直接将通用开源 RAG 应用作为核心底座，避免权限、版本、质量和升级能力受其领域模型限制；可按需复用独立组件。

## 4. 企业 RAG 长期功能图谱

长期能力分为十二个域：

1. 数据源与连接器；
2. 文档解析与知识加工；
3. 索引与知识存储；
4. 检索与排序；
5. 模型与回答生成；
6. 知识库运营；
7. 应用构建与开放集成；
8. 身份、租户与权限；
9. 安全与合规；
10. 评测与质量体系；
11. 可观测性与成本治理；
12. 平台工程与运维。

建设阶段分为：

- 0→1：形成可用、可评测的制度问答闭环；
- 1→10：支持多部门正式使用，补充统一身份、连接器、文档级权限和运营能力；
- 10→N：建设规模化、高可用、合规、插件化和生态能力。

## 5. 用户角色

### 5.1 普通员工

- 在授权知识库中提问和追问；
- 查看引用及原文；
- 查看个人会话；
- 点赞、点踩并提交反馈。

### 5.2 知识管理员

- 管理负责的知识库；
- 上传、更新、发布、下线文档；
- 查看解析、分块和索引状态；
- 重试失败任务；
- 维护文档元数据和有效期；
- 查看反馈、维护评测样本和分析坏例。

### 5.3 平台管理员

- 管理用户、角色和知识库权限；
- 管理模型、Prompt 和系统配置；
- 查看队列、任务、健康状态和审计日志；
- 管理 API Key、备份和恢复。

### 5.4 质量运营

首版作为知识管理员的附加权限，不单独建立固定角色。负责评测集、版本对比、人工评审和坏例闭环。

## 6. 第一版功能范围

### 6.1 身份与权限

- 本地账号登录；
- 用户创建、禁用、密码重置；
- 平台管理员、知识管理员、普通员工三个基础角色；
- 用户或用户组到知识库的 VIEW/MANAGE 授权；
- 服务端统一鉴权；
- 检索、引用、预览和下载统一执行权限检查；
- 权限变更触发权限版本更新和缓存失效；
- 管理操作写入审计日志。

第一版权限粒度为知识库级，数据模型预留文档级 ACL 扩展点。

### 6.2 知识库管理

- 创建、编辑、停用和归档知识库；
- 配置名称、描述、所属部门、负责人；
- 管理知识管理员和访问者；
- 查看文档数量、处理状态和当前索引发布版本；
- 配置默认检索和生成策略。

知识库状态：DRAFT、ACTIVE、DISABLED、ARCHIVED。

### 6.3 文档管理

第一版支持 PDF、DOCX、TXT 和 Markdown。扫描件 OCR 在样本确认存在强需求时纳入，否则作为后续扩展。

功能包括：

- 单文件和批量上传；
- 文件类型、大小、安全和哈希校验；
- 标题、分类、标签、生效与失效日期；
- 文档版本管理；
- 处理状态和错误原因；
- 手动重试；
- 原文、解析结果和分块预览；
- 发布、下线、归档和删除。

上传完成与可用于问答是不同状态。

### 6.4 知识加工

默认采用结构优先分块，固定 Token 长度和重叠窗口作为降级策略。

加工步骤：

```text
安全检查 → 格式识别 → 内容解析 → 清洗 → 结构识别
→ 分块 → 元数据增强 → Embedding → 索引 → 验证 → 待发布
```

每个步骤均记录状态、输入输出引用、尝试次数、耗时和错误；支持幂等、自动重试、死信和从失败步骤继续。

每个 Chunk 至少保存：

- 知识库、文档及文档版本 ID；
- 顺序号、正文和内容哈希；
- 标题层级路径；
- 页码或段落位置；
- 标签、生效时间和权限信息；
- Token 数和分块配置版本。

### 6.5 检索与排序

在线检索流程：

```text
问题规范化
→ BM25 关键词召回 + 向量召回
→ 融合与去重
→ 权限、状态、版本和有效期过滤
→ Rerank
→ 相邻片段扩展
→ 多样性与单文档数量控制
→ Token 预算裁剪
→ 最终证据上下文
```

第一版支持：

- 混合检索；
- 知识库范围和权限过滤；
- 文档状态、版本和有效期过滤；
- Top K、阈值及融合参数；
- Rerank；
- 去重和上下文组装；
- 无结果状态；
- 检索候选和排名 Trace。

暂不加入 GraphRAG、自由问题规划、多代理搜索和复杂查询分解。

### 6.6 问答与引用

- 知识库入口和会话管理；
- SSE 流式回答；
- 有限多轮追问；
- 中止和重新生成；
- 来源编号、文档标题、页码或章节、引用原文；
- 引用点击后原文定位；
- 请求追踪 ID；
- 明确拒答状态和原因；
- 生成后引用合法性校验。

模型只能使用授权检索上下文回答。资料不足时不得用模型通用知识补全企业制度。

### 6.7 模型网关

基于 Spring AI 2.0 统一承载：

- ChatModel / ChatClient；
- EmbeddingModel；
- 流式输出；
- 模型配置和健康检查；
- 超时、重试、并发限制和主备降级；
- Token、耗时和错误统计；
- 本地模型和外部模型 API 适配。

Rerank 采用平台自有 `RerankProvider` 接口，在 Spring AI 标准能力不能覆盖目标服务时提供适配实现。

每个模型配置声明数据出域策略。禁止数据出域的知识库不得将问题或上下文发送给外部模型。

### 6.8 配置版本

以下对象必须版本化：

- 原始文档和解析产物；
- 分块配置；
- Embedding 配置；
- 索引发布版本；
- 检索配置；
- Prompt；
- 生成配置和模型部署；
- 评测集。

已发布配置不可原地修改，只能创建新版本。每次问答和评测必须绑定实际使用的全部版本。

### 6.9 评测与反馈

- 黄金问题集和版本；
- 批量离线评测；
- 检索、回答、引用和拒答指标；
- 两个配置版本对比；
- 单条结果和完整证据链；
- 裁判模型评分及原始记录；
- 人工 PASS、MINOR_ISSUE、FAIL 评审；
- 点赞、点踩和原因分类；
- 线上坏例转入评测集；
- 坏例归因和处理状态。

第一版从至少 50 条真实问题起步，试点前扩充至 100–200 条。

### 6.10 Trace 与监控

每个 QueryRun 关联：

- 用户及权限版本；
- 原始及规范化问题；
- 知识范围和索引版本；
- 召回及 Rerank 结果；
- 最终上下文；
- Prompt、模型和配置版本；
- 回答、引用和拒答；
- 阶段耗时、Token、错误和降级；
- 用户反馈。

Spring AI Observability、Micrometer 和 OpenTelemetry 用于框架层指标和 Span。提示词、回复、工具参数及向量检索正文保持默认不记录。需要回放的正文进入平台受控 Trace 存储，并实施独立授权、脱敏和保留期。

### 6.11 开放 API

- 创建知识库；
- 上传文档和查询状态；
- 发起问答和获取 SSE 流；
- 查询引用；
- 提交反馈；
- 健康检查；
- API Key、权限范围、吊销、限流、请求 ID 和统一错误码；
- OpenAPI 文档。

### 6.12 私有化交付

- Docker 镜像；
- Docker Compose 开发和演示环境；
- Kubernetes / Helm 部署；
- 数据库迁移；
- 配置及密钥外置；
- 健康检查和日志收集；
- 基础监控告警；
- 备份、恢复和索引重建；
- 受限网络环境镜像导入；
- 管理员初始化和系统版本展示。

## 7. 总体架构

采用“模块化单体 + 独立异步 Worker + 可替换基础设施”。首期不提前微服务化。

### 7.1 运行单元

1. Web Console：员工问答、知识管理、评测和平台管理；
2. Platform API：Spring Boot 模块化单体；
3. Ingestion Worker：Java/Spring 主链路，可独立扩容；
4. Evaluation Worker：离线评测任务，可与 Ingestion Worker 共享部署但保持逻辑模块分离；
5. Python Document Intelligence Service：可选扩展，仅用于 OCR、复杂版面或多模态解析；
6. Model Serving：企业内网模型推理服务或受控外部 API。

### 7.2 控制面

负责身份权限、知识库、文档生命周期、配置版本、索引发布、评测、审计和管理员操作。

### 7.3 数据面

负责文档加工、在线检索、模型推理、流式回答、权限执行和运行 Trace。

首期控制面和在线数据面可以部署在同一 Platform API 中，但代码模块和接口必须分离。

### 7.4 拆分条件

仅在以下情况出现时拆服务：

- 解析需要独立扩容或资源隔离；
- 在线 SLA 被后台任务影响；
- 模型网关被多个产品复用；
- 模块发布节奏和团队边界发生冲突；
- 模块需要独立安全边界。

## 8. Spring AI 2.0 落位

### 8.1 使用范围

- `ChatClient` / `ChatModel`：模型调用和流式生成；
- `EmbeddingModel`：文档和查询向量化；
- `RetrievalAugmentationAdvisor`：标准 RAG 编排骨架；
- `DocumentRetriever`：企业检索扩展边界；
- `DocumentPostProcessor`：Rerank、过滤、去重和上下文压缩；
- `Advisor`：查询规范化、生成策略、引用校验和 Trace 等横切逻辑；
- Spring AI ETL/Reader：解析适配器之一；
- Spring AI Observability：框架层指标和 Trace。

### 8.2 平台自有能力

Spring AI 不拥有以下领域模型：

- Document、DocumentVersion、IndexRelease；
- 知识库权限和 ACL；
- 文档加工状态机；
- 混合检索和发布索引；
- QueryRun；
- Prompt、模型、索引及评测版本；
- 引用证据和质量门禁。

### 8.3 Advisor 链

建议组合小型 Advisor：

```text
AuthorizationContextAdvisor
→ QueryNormalizationAdvisor
→ EnterpriseRetrievalAdvisor
→ EvidenceContextAdvisor
→ GenerationPolicyAdvisor
→ CitationValidationAdvisor
→ QueryTraceAdvisor
```

ACL 仍须在自定义 `EnterpriseDocumentRetriever` 中强制执行，Advisor 不是唯一安全边界。过滤表达式必须由后端生成，不接受用户任意查询表达式。

### 8.4 自有扩展接口

```text
DocumentParser
Chunker
EmbeddingProvider（由 Spring AI 适配）
SearchIndex
EnterpriseDocumentRetriever
HybridSearchService
RerankProvider
ContextAssemblyService
ChatModelProvider（由 Spring AI 适配）
CitationValidator
RefusalPolicy
RagExecutionTrace
```

## 9. 核心领域模型

### 9.1 身份域

- User：用户身份、状态及身份源；
- Role：PLATFORM_ADMIN、KNOWLEDGE_ADMIN、EMPLOYEE；
- UserGroup：为部门和统一身份同步预留；
- KnowledgePermission：USER/GROUP 到知识库 VIEW/MANAGE 的授权；
- permissionVersion：权限变更后更新，用于缓存失效和查询审计。

### 9.2 知识域

- KnowledgeBase：知识库状态、负责人、默认检索/生成配置和当前索引发布版本；
- Document：逻辑文档，保存标题、分类、状态、来源、有效期和当前发布版本；
- DocumentVersion：具体文件版本，保存文件引用、哈希、处理状态及配置版本；
- ParsedDocument：解析产物及结构化内容引用；
- DocumentChunk：文档版本派生的可检索片段。

同一文档同一时间最多一个在线版本，Chunk 不跨文档版本复用 ID。

### 9.3 索引域

- IndexBuild：一次文档版本索引构建；
- IndexRelease：知识库可发布索引快照，状态为 BUILDING、VALIDATING、READY、ACTIVE、FAILED、RETIRED；
- KnowledgeBase.currentIndexReleaseId：在线查询唯一入口。

新版本验证成功后通过索引别名和数据库指针原子发布。处理完成的文档不会自动进入线上。

### 9.4 模型和配置域

- ModelProvider：供应商、Endpoint、加密凭据和网络策略；
- ModelDeployment：CHAT、EMBEDDING、RERANK 模型部署；
- RetrievalProfileVersion；
- GenerationProfileVersion；
- ChunkingProfileVersion；
- PromptVersion。

每个索引发布版本绑定唯一 Embedding 模型版本、向量维度和归一化策略。更换 Embedding 模型必须重建索引。

### 9.5 问答域

- Conversation 和 Message；
- QueryRun：一次完整执行，状态为 RECEIVED、RETRIEVING、RERANKING、GENERATING、VALIDATING、COMPLETED、REFUSED、FAILED、CANCELLED；
- RetrievalHit：召回渠道、各阶段分数、排名、是否进入上下文和过滤原因；
- GenerationRun：模型、Prompt、上下文哈希、Token、耗时和降级；
- Citation：答案位置、Chunk、文档版本、来源位置、引用文本和校验状态。

### 9.6 评测域

- EvaluationDataset / DatasetVersion；
- EvaluationCase；
- EvaluationRun；
- EvaluationCaseResult；
- UserFeedback。

所有评测运行绑定数据集、索引、检索、Prompt 和模型版本。

## 10. 文档状态机与知识加工链路

### 10.1 文档版本处理状态

```text
UPLOADED → QUEUED → PROCESSING → READY
                            ↘ FAILED
                            ↘ CANCELLED
```

内部处理步骤为 EXTRACTING、CLEANING、STRUCTURING、CHUNKING、EMBEDDING、INDEXING、VALIDATING。

发布状态为 DRAFT、PUBLISHED、OFFLINE、SUPERSEDED。

### 10.2 上传

```text
鉴权 → 文件校验和安全扫描 → 哈希
→ 对象存储 → 创建 DocumentVersion → Outbox → 异步任务
```

上传接口不执行同步解析，只返回文档版本和任务状态。

### 10.3 幂等与可靠消息

步骤幂等键由以下信息组成：

```text
documentVersionId + pipelineVersion + stepName + inputHash
```

采用事务 Outbox 发布消息；消息按至少一次投递设计；消费者负责幂等；失败使用指数退避和最大重试次数，超过次数进入死信队列。

旧任务不得覆盖新文档版本结果，关键状态更新使用乐观锁。

### 10.4 发布

```text
DocumentVersion READY
→ 管理员检查
→ 加入候选 IndexRelease
→ 完整性和质量验证
→ 原子切换索引别名及当前发布指针
→ DocumentVersion PUBLISHED
```

更新失败时旧版本保持在线。

### 10.5 下线与删除

下线顺序：

```text
控制面立即标记不可查询
→ 在线过滤即时生效
→ 发布不含该文档的新索引版本
→ 异步清理索引
```

下线保留内容和版本；删除进入受控数据清理流程。历史引用能否打开取决于当前权限和数据保留策略。

## 11. 在线问答链路

### 11.1 请求接收

```text
认证 → 账号状态 → 限流 → 服务端计算知识范围
→ 创建 QueryRun → 执行检索和生成
```

客户端指定的知识库只能与服务端授权范围取交集。

### 11.2 查询处理

第一版仅执行空白和标点规范化、有限指代补全及明显时间/类别过滤提取。保留原始问题，可同时使用原始及规范化问题检索。暂不进行不可控的自由改写。

### 11.3 召回与排序

初始建议为关键词和向量各召回 Top 30，经 RRF 或评测选定的加权方式融合，之后 Rerank。具体参数必须由黄金集和容量测试确定，不能作为固定产品假设。

检索必须过滤：

- 用户授权知识库；
- 当前有效文档和文档版本；
- 当前 IndexRelease；
- 文档状态、生效和失效日期；
- 后续文档级 ACL。

### 11.4 上下文与生成

上下文组装考虑相关性、完整性、来源多样性、文档权威性、生效时间和 Token 预算。每个证据片段有稳定来源编号。

模型必须：

- 仅使用给定证据；
- 事实结论附带来源；
- 证据不足时拒答；
- 证据冲突时明确指出；
- 不隐藏不确定性。

### 11.5 引用校验

生成后校验：

- 引用编号是否存在；
- 引用是否属于当前上下文；
- 事实性答案是否缺少引用；
- 用户是否仍有引用权限；
- 文档是否在生成期间紧急下线。

### 11.6 拒答

拒答是正常业务结果，不是系统失败。内部原因包括：

- NO_RELEVANT_EVIDENCE；
- INSUFFICIENT_EVIDENCE；
- OUT_OF_SCOPE；
- CONFLICTING_EVIDENCE；
- CONTENT_NOT_EFFECTIVE；
- ACCESS_RESTRICTED；
- SAFETY_POLICY。

普通用户不能从 ACCESS_RESTRICTED 推断无权限文档存在，统一显示当前可访问知识范围内证据不足。

### 11.7 流式事件

```text
run.started
retrieval.completed
answer.delta
citation.available
answer.completed
answer.refused
run.failed
```

用户取消时终止下游模型调用，QueryRun 标记 CANCELLED，并记录已发生的 Token 和费用。

## 12. 技术选型

### 12.1 应用技术

- 前端：React、TypeScript、成熟企业 UI 组件库、SSE；
- 后端：Java、Spring Boot 4、Spring AI 2.0 GA；
- 模块治理：可采用 Spring Modulith；
- Python 扩展：独立服务，不直接修改核心业务状态。

### 12.2 基础设施

- PostgreSQL：业务事实来源；
- S3 兼容对象存储（如 MinIO）：原文件、解析产物和大型 Trace；
- OpenSearch：BM25、向量、元数据过滤、索引别名；
- Redis：缓存、限流、短期会话和协调，不保存唯一业务事实；
- RabbitMQ：知识加工、索引、评测和清理任务；
- OpenTelemetry、Prometheus、Grafana 和集中日志系统；
- Docker Compose、Kubernetes 和 Helm。

若企业已有统一 Kafka、对象存储、搜索或可观测平台，可通过适配接口复用；第一版不同时运维全文搜索、独立向量库和图数据库。

### 12.3 存储原则

PostgreSQL 保存领域事实。对象存储和搜索索引均可根据数据库、原文件和配置版本重建。Redis 清空不得造成业务事实丢失。

## 13. 部署和容量

### 13.1 资源隔离

至少逻辑隔离：

- 在线 Web/API；
- Ingestion Worker；
- Evaluation Worker；
- 模型推理；
- PostgreSQL；
- OpenSearch。

批量上传和评测不得不可接受地影响在线问答。通过独立队列、并发上限、资源 Request/Limit 和节点策略控制。

### 13.2 容量基线

容量由总页数、Chunk 数、向量维度、副本、每日增量、查询并发和上下文长度决定，不能只依据文档数。

首版使用真实样本完成 100 万–500 万 Chunk 压测，输出：

- 索引和磁盘占用；
- 检索 P95/P99；
- 文档加工吞吐；
- Embedding 速率和成本；
- Worker 扩缩效果；
- 在线与离线任务相互影响；
- 容量增长和告警阈值。

### 13.3 可用性基线

- Worker 故障不丢任务；
- API 重启不丢会话和配置；
- 新文档失败不影响旧版本在线；
- 索引可以重建；
- 至少保留当前和一个可回滚索引版本；
- 上线前完成一次真实备份恢复演练。

## 14. 安全设计

### 14.1 信任区域

- 用户访问区：浏览器、门户和 API 调用方；
- 应用服务区：Web、API、Worker 和模型网关；
- 数据区：数据库、对象存储、搜索、缓存和队列；
- 模型区：企业内网模型和受控外部出口。

数据组件默认不暴露给用户网络。外部模型只能通过统一网关访问。

### 14.2 上传安全

- 按文件内容识别类型；
- 限制文件大小、页数、解析时间、内存和临时磁盘；
- 防止路径穿越、压缩炸弹、宏和恶意嵌入对象；
- 解析器运行在受限 Worker；
- 普通用户不可见敏感堆栈；
- 文档内容视为不可信数据，不视为系统指令。

### 14.3 RAG 安全

- 检索前强制 ACL；
- 模型无法主动访问其他知识库；
- 缓存键包含知识范围和权限版本；
- 原文使用后端代理或短期授权 URL；
- 引用和预览重新鉴权；
- QueryRun 保存授权范围快照；
- 外部模型遵守知识库出域策略；
- 密钥加密保存且不进入日志；
- 完整 Trace 独立授权和保留。

### 14.4 Prompt 注入

系统明确区分系统规则、用户问题和检索证据。通过权限、工具授权、输出检查和网络策略形成纵深防御，不依赖 Prompt 文案作为唯一防线。

## 15. 异常与降级

### 15.1 在线链路

- 一路检索失败：使用另一路并记录降级；
- 两路均失败：返回系统错误，不伪装无答案；
- Rerank 超时：退回融合排序；
- 主模型失败：仅在策略允许时切换备用模型；
- 禁止出域：改用本地模型，否则明确失败；
- 引用校验失败：保守回答、有限重试或拒答；
- 权限变化：重新鉴权；
- 文档紧急下线：完成前再次校验引用。

### 15.2 加工链路

- 临时网络、限流和组件不可用：指数退避重试；
- 文件损坏、不支持或无有效内容：不可重试并给出可理解错误；
- 配置不兼容：暂停相关任务并告警；
- 部分 Chunk 索引失败：整个文档版本不可发布；
- 索引验证失败：不得切换线上别名。

### 15.3 评测链路

- 单条系统失败不终止整个批次；
- 区分答案失败和系统失败；
- 运行中配置不可变；
- 不完整运行不得作为发布门禁。

## 16. 质量与测试策略

### 16.1 软件测试

- 单元测试：状态机、权限、排名融合、预算、引用、拒答、路由、幂等和审计；
- 模块集成测试：使用 Testcontainers 启动 PostgreSQL、OpenSearch、RabbitMQ、Redis 和对象存储；
- Spring AI 契约测试：ChatModel、EmbeddingModel、RerankProvider 的调用、流式、超时、取消、限流和异常；
- 端到端测试：覆盖知识库创建、授权、文档发布、问答、引用、反馈和评测；
- 安全测试：ID 枚举、越权、缓存、旧 URL、权限撤销和 Prompt 注入；
- 稳定性测试：服务重启、消息重复、组件中断、队列积压和备份恢复。

### 16.2 解析指标

- 文本提取成功率；
- 页面覆盖率；
- 标题结构准确率；
- 表格完整率；
- 乱码和重复比例；
- 页码定位准确率；
- Chunk 可读性；
- 处理成功率和耗时。

### 16.3 检索指标

- Recall@K；
- MRR；
- NDCG@K；
- 正确文档和 Chunk 命中率；
- 无关片段比例；
- 过期文档召回率；
- 无权限召回数，必须为 0。

### 16.4 生成指标

- 正确性；
- 忠实性；
- 完整性；
- 相关性；
- 引用准确率和完整率；
- 正确拒答率和错误拒答率。

### 16.5 系统指标

- 检索、Rerank、首字和完整回答 P50/P95/P99；
- 成功率、拒答率和降级率；
- Token 使用量和成本；
- 文档处理吞吐、失败率和队列时间；
- CPU、内存、磁盘和 GPU 状态。

### 16.6 自动和人工评测

确定性指标优先作为回归依据。裁判模型用于忠实性、相关性和完整性辅助评分，但必须保存裁判模型、Prompt、输入、原始输出和解析结果，且不能作为唯一发布门禁。

关键制度问题由人工评审决定，等级为 PASS、MINOR_ISSUE、FAIL。

## 17. 黄金评测集

第一版问题类型建议覆盖：

- 直接事实 20%；
- 条件规则 20%；
- 流程步骤 15%；
- 例外情况 15%；
- 跨段落总结 10%；
- 时间与版本 5%；
- 多文档冲突 5%；
- 应当拒答 10%。

问题优先来源于员工真实提问、知识负责人、历史咨询和线上坏例，不以模型自动生成作为主要来源。

已发布评测集不可原地修改；开发集和验收集分离；关键验收集避免用于反复调参。

## 18. 数据保留与恢复

默认策略可按企业规范调整：

- 原始文档：文档生命周期内保留；
- 历史版本：默认保留，支持受控清理；
- 解析和 Chunk：与文档版本一致；
- 在线索引：当前版和至少一个回滚版；
- 会话：默认 180 天；
- 完整 Query Trace：默认 30–90 天；
- 审计日志：默认不少于 180 天；
- 模型密钥：加密保存，不进入日志和 Trace。

恢复顺序：

```text
PostgreSQL → 对象存储 → 配置和凭据
→ OpenSearch 快照恢复或完整重建
→ IndexRelease 校验 → 恢复流量
```

## 20. 首版验收标准

### 20.1 产品门禁

- 员工可快速发起制度问答；
- 非拒答答案具有可打开的原文引用；
- 管理员可独立上传、检查、发布和下线文档；
- 点踩可关联完整 QueryRun；
- 配置版本可使用同一评测集比较。

### 20.2 正确性门禁

- 权限泄露为 0；
- 关键制度问题严重事实错误为 0；
- 引用能支持对应结论；
- 无依据问题能够拒答；
- 新版本无无法解释的显著回归。

Recall@K、引用准确率和性能等具体阈值在第 1–2 周用真实数据建立基线后，经产品、技术和知识负责人共同批准，作为后续发布门禁。门禁批准动作必须留有版本和审计记录。

### 20.3 可靠性门禁

- 消息重复不产生重复 Chunk；
- Worker 中断后任务可恢复；
- 新文档失败不影响旧版本；
- 发布失败不形成半完成线上索引；
- 文档下线立即停止进入新查询；
- Redis 丢失不丢业务事实；
- 完成实际恢复演练。

### 20.4 运维门禁

- 服务具有健康检查；
- 关键错误和积压有告警；
- 模型凭据不进入日志；
- Token、调用耗时和任务状态可观测；
- 部署和升级可重复执行；
- 系统及配置版本可查询。

## 23. 关键架构决策摘要

1. 采用场景优先而非底座优先；
2. 采用模块化单体和独立 Worker，不提前微服务化；
3. 使用 Spring Boot 4 和 Spring AI 2.0 GA 作为 Java 主技术栈；
4. Python 仅作为复杂文档智能扩展服务；
5. PostgreSQL 是业务事实来源；
6. OpenSearch 统一承担首版全文和向量检索；
7. Document 与 DocumentVersion 分离；
8. 文档处理完成不等于自动发布；
9. 在线查询绑定明确 IndexRelease；
10. 权限覆盖检索、引用、预览、缓存和 Trace；
11. QueryRun 关联全部证据和配置版本；
12. 异步链路采用 Outbox、至少一次投递和幂等消费；
13. 质量评测和坏例闭环属于 P0；
14. Spring AI 是模型和 RAG 编排框架，不拥有平台领域模型；
15. 上线前必须通过权限、容量、故障恢复和备份恢复验证。

Veridex 受限网络安装指南
========================

前置：目标环境已有 Kubernetes 1.28+、Helm 3.13+、docker（或 nerdctl/containerd 工具链）、
PostgreSQL 17 / RabbitMQ 4 / MinIO / OpenSearch 3.2 /（可选）OTel Collector，以及企业镜像仓库。

1. 生成离线包（联网机器，仓库根目录）：
     ./scripts/verify-deployment.sh 1          # 构建应用镜像
     OFFLINE_DIR=/path/to/veridex-offline deploy/offline/scripts/export-images.sh
   多架构发布镜像（amd64/arm64 manifest，可选但验收标准要求该路径可用）：
     docker buildx build --platform linux/amd64,linux/arm64 \
       -f backend/Dockerfile -t <REGISTRY>/veridex-backend:0.1.0 --push .
     docker buildx build --platform linux/amd64,linux/arm64 \
       -f web/Dockerfile -t <REGISTRY>/veridex-web:0.1.0 --push .

2. 转移 veridex-offline/ 目录到目标环境。

3. 导入镜像（二选一）：
   a. docker load：deploy/offline/scripts/import-images.sh
   b. 推送到私有 registry：
        REGISTRY=registry.corp.example:5000 deploy/offline/scripts/push-images.sh

4. 准备 existing Secret（chart 不创建，禁止明文入库）：
     kubectl create namespace veridex
     kubectl -n veridex create secret generic veridex-secret \
       --from-literal=db-username=... \
       --from-literal=db-password=... \
       --from-literal=rabbitmq-username=... \
       --from-literal=rabbitmq-password=... \
       --from-literal=minio-access-key=... \
       --from-literal=minio-secret-key=... \
       --from-literal=session-secret=...
   若启用 trace body capture（ERRORS/ALL），还需追加 trace-fingerprint-key /
   trace-current-key-id / trace-current-key（以及可选 trace-historical-keys）。

5. 编写 values（endpoint 指向企业基础设施；出口依赖用 selector 或 CIDR 显式声明，
   参见 deploy/helm/veridex/values.yaml 注释），并合并 registry 覆盖：
     helm upgrade --install veridex deploy/offline/veridex-offline/charts/veridex-<version>.tgz \
       -n veridex -f my-values.yaml -f veridex-offline/values/registry-values.yaml

6. 等待 rollout 并冒烟：
     kubectl -n veridex rollout status deploy/veridex-veridex-backend
     kubectl -n veridex port-forward svc/veridex-veridex-web 8080:80
     VERIDEX_WEB_URL=http://127.0.0.1:8080 deploy/compose/smoke.sh

模型配置（必读）
----------------
- ⚠️ **真实问答/检索必须配好 Chat 与 Embedding 模型，不要用默认 deterministic。**
  默认 deterministic 是 128 维无语义哈希 / 模板占位，跑不出真实结果，只用于无外部依赖的离线冒烟。
- Chat 对话模型（二选一）：
  * deepseek：values 设 VERIDEX_CHAT_PROVIDER=deepseek + VERIDEX_DEEPSEEK_API_KEY；
  * Ollama：VERIDEX_CHAT_PROVIDER=ollama + VERIDEX_OLLAMA_BASE_URL + VERIDEX_OLLAMA_CHAT_MODEL。
- Embedding 向量模型（**必须**切 Ollama，否则向量检索基本失效）：
  VERIDEX_EMBEDDING_PROVIDER=ollama + VERIDEX_EMBEDDING_DIMENSIONS=1024 + VERIDEX_OLLAMA_EMBEDDING_MODEL=qwen3-embedding:0.6b。
- Ollama 与模型权重（qwen3:8b / qwen3-embedding:0.6b 或自定义）由安装者预置，不打入本交付包。
- 启用 Ollama 时：在 networkPolicy.externalEgress 显式放行 Ollama 的 selector/CIDR + 11434 端口
  （chart 默认不开放 Ollama 出站）。
- Ollama 经 HTTP 时必须同时设 VERIDEX_OUTBOUND_ALLOWED_HOSTS / VERIDEX_OUTBOUND_ALLOWED_PORTS
  / VERIDEX_OUTBOUND_ALLOW_INSECURE_HTTP=true（后端出站策略 fail-fast）。
- deepseek 时放行 api.deepseek.com:443；出站策略同样需在 externalEgress 显式声明。

排障：Secret 缺 key 或 backend 安全配置非法时 Pod 不 ready，日志只输出固定配置错误码；
Secret 值原地变更后执行 kubectl -n veridex rollout restart deploy/veridex-veridex-backend。

备份 / 恢复（k8s）
-----------------
- Veridex 不内置备份调度器；备份与恢复由安装者自行编排。仓库提供脚本与语义
  （deploy/backup/backup.sh、restore.sh、verify-recovery.sh），本附录给出 k8s 侧落地方式。

- 备份内容与语义：
  * PostgreSQL：pg_dump 逻辑备份，含 Flyway schema_version、全部业务数据与
    Spring Session 会话表（Session 已外置于 PG，随备份恢复）。
  * MinIO：对象导出（mc mirror 语义，对象键结构原样保留）。
  * OpenSearch：**不备份**——恢复走源重建（reindex 语义，spec D1）。
  * 备份产物目录含 manifest.json 与 SHA256SUMS，恢复前须校验完整性。

- k8s 侧调度建议：以 CronJob 在 veridex 命名空间按保留策略周期执行 pg_dump 与
  对象导出，输出写挂载的 PV（容量与保留窗口由安装者按数据量规划）或对接企业备份存储。
  备份命令参考（需在可访问 PostgreSQL/MinIO 的 Pod 或 job 内执行）：
    pg_dump -Fc -h <PG_HOST> -U veridex -d veridex > postgres.dump
    mc mirror <MINIO_ALIAS>/veridex-documents ./objects
  （与 deploy/backup/backup.sh 的产物布局保持一致，便于复用恢复脚本语义。）

- 恢复（引用仓库脚本语义，按需裁剪）：
    1. 恢复 PostgreSQL（pg_restore）→ 校验 Flyway 迁移版本兼容；
    2. MinIO 对象回灌（mc mirror 反向）；
    3. OpenSearch 源重建（一次性 reindex 任务，按 KB 发布新 IndexRelease）；
    4. 冒烟 + 问答抽查。完整流程与 RTO 口径见 deploy/backup/verify-recovery.sh
      （2026-08-19 实测 RTO=21s：销毁 → smoke 通过，不含 QA 抽查；
       1M 规模 RTO 见 docs/capacity-report-2026-08.md）。
